# 用户全表注册协调

## 用途与当前启用边界

[MiddlewareUserSyncService](../../../app/service/middleware_user.py) 是启动注册与显式首次登录共用的注册协调器，使用已有平台会话，以 `knowledge-accumulation` 身份发布完整人员表。知识后端负责全表注册和显式登录；registry 负责用户增量更新、权限和 SQL 管理员关系编辑/中央增量维护，知识后端不调用 `POST user/update`。

> **自动启动同步：** 用户已确认中间件完成适配，MIDDLEWARE_USER_SYNC_ENABLED 已从代码、实际 `.env` 和示例移除。配置中间件接入后，应用启动自动注册用户表及管理员表；没有独立启停开关。是否实际发布成功需核对运行日志中的用户 count 及管理员 admin_count，不能只依据应用启动成功判断。

职责及跨后端覆盖限制的唯一完整说明见[登录与会话管理](../../architecture/system/user-auth.md#中间件维护方授权与运维状态)。本地锁不能阻止 registry 增量更新被旧全表覆盖。

## 数据流与失败处理

启动任务非阻塞等待平台 token，不提前查询数据库；取得同一维护锁后读取完整员工快照、优先保留 SQL 开发身份，仅补充尚未落库的模拟身份、校验唯一 userid，再发布全表。用户阶段成功严格校验 count 后继续管理员阶段；两阶段均完成才退出。管理员失败仅重试管理员，不重发用户表，规则见[启动管理员全表同步](startup-admin-sync.md)。用户阶段失败脱敏记录并重读重试，不周期同步。数据库错误、非法资料及冲突不能降级为空表；真实空表按外部删除语义处理。

显式生产或开发 POST login 先生成随机用户 token 并尝试 PUT 绑定；中央已有资料时无需全表。只有 PUT 明确返回既有契约的资料缺失错误（404、detail 为“用户不存在，请先同步用户信息”）才进入登记：

1. 丢弃该 userid 的旧成员确认，调用 `ensure_registered_locked(userid)`，重新读取完整权威表；必须包含目标用户，配置不得覆盖已有 SQL 开发身份，SQL userid 重复必须拒绝。
2. 严格校验 full-table count，成功后仅记录成员集合，不缓存权限。前台成功满足启动任务的用户阶段；管理员阶段仍由启动任务独立完成。
3. 使用本次同一随机 token 最多再 PUT 一次，成功后才向客户端返回。第二次失败直接返回 503，不无限重发全表。

中央资料缺失时始终允许按既定 404 契约受控补登记，注册失败仍返回 503。普通 404、网络故障、401/403/409 或非法响应不被当成登记依据。GET me 及普通请求只用 access_token 查询中央，不注册、不 PUT、不复活旧 token。中央 PUT 与 POST 的精确 token 契约见[登录与会话管理](../../architecture/system/user-auth.md#本地与中央会话规则)。

启动与登录共享组合根注入的唯一维护锁，锁覆盖完整快照读取至发布，以及显式登记至登录确认。总超时包含排队；取消释放锁，401 仅失效本次使用的平台 token。锁顺序及进程限制见[并发协调](../../architecture/system/user-auth.md#全表同步与登录并发协调)。

## 中间件调用契约

出站请求为 `POST /middleware-service/api/user/full-table`，使用本项目平台 Bearer，精确 body：

```json
{"users":[{"userid":"employee-a","username":"员工甲","permissions":{"registry":0},"departments":["综合管理部","总经办"]}]}
```

映射只取[权威员工现有字段](../../architecture/data/personnel.md#中间件资料映射)，用户资料 DTO 显式发送完整部门名称列表，不发送部门 ID、头像、管理员关系或用户 token，不重新生成已有员工等级。成功响应 `200 {"count":1}` 中 count 必须为严格整数且等于提交数量。

本协调器不调用登录缓存接口；**full-table 可能删除遗漏用户及其登录缓存**。它不发送用户心跳、不周期发布、不在关闭时清空中央表。PUT 只由显式认证服务在登记后执行。外部参考见相邻中间件项目的 `description/api/user.md`，最终职责以用户划分为准。

## 配置与生命周期

| 配置项 | 默认值 | 用途 |
| --- | --- | --- |
| `MIDDLEWARE_USER_SYNC_OPERATION_TIMEOUT_SECONDS` | `30` | 一次完整读取和发布的总超时。 |
| `MIDDLEWARE_USER_SYNC_RETRY_INTERVAL_SECONDS` | `30` | 后台失败重试间隔；无 token 时最长每秒检查。 |

示例见 [.env.example](../../../.env.example)。配置中间件接入时，组合根共用员工仓库、HTTP 客户端、单个平台会话与注册协调器；中间件接入配置存在即创建启动发布任务；未配置接入时不创建依赖，认证请求返回 503。MySQL 惰性连接、不自动建表。登录不再单独关闭，生产应用启动需要钉钉凭据，且不合并模拟用户；独立注册协调器本身仍不依赖钉钉。

停止时先取消并等待注册任务，再逆序清理认证资源、HTTP 客户端、仓库及平台会话。无重复平台登录或心跳任务，无停机远程清表。

## 切换前待对齐事项

1. 用户已确认中间件适配，部署侧仍须保证 full-table 与 PUT 使用本项目身份的实际授权；`POST user/update` 明确归 registry，不等待为本项目授权。
2. 确认与 registry 共用同一权威人员权限源，权限编辑先持久化该源，完整范围无遗漏。开发配置不得覆盖真实员工。
3. 由用户协调旧快照与 registry 增量编辑的跨后端覆盖保护；进程内锁和唯一全表发布方不能替代该契约。
4. 用户安排停止 registry 旧全表任务后再切换，核对遗漏用户及登录缓存的删除范围。

注册迁移阶段不更改其他项目、实际配置、共享数据或真实头像；不复制密钥、不清理来源。
