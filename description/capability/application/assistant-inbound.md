# 钉钉消息入站与整条校验

## 用途与边界

[入站服务](../../../app/service/robot_inbound.py)把可信钉钉单聊消息转换为中间件 `user_message` 任务，随后由既有[助理消费者](assistant-consumption.md)领取、执行和交付。这里负责校验、首次员工初始化、可靠接收和发布，不调用模型，不创建中央登录，不覆盖已有员工权限。

`ASSISTANT_ENABLED=false` 时不启动入站。启用后由[应用生命周期](../../../app/main.py)装配 Stream、接收器及待发布扫描器；2026-10-30 已观察到真实消息进入共享队列并被助理执行，最终转换失败；该记录不代表完整收发验收通过，见[真实任务观察](../infrastructure/dingtalk-robot.md#真实任务观察与验证边界)。钉钉配置与可信企业身份边界见[机器人接入](../infrastructure/dingtalk-robot.md)。

## 整条消息规则

**一条消息只要有一个不支持的附件，整条拒绝。** 文字、其他合法附件都不单独入队；同一规则适用于文字与附件混合、多个附件及单个附件，不另设部分接收模式。

| 内容 | 接收规则 |
| --- | --- |
| 纯文字 | 保留正文，不添加虚构附件；空白输入或超长正文不能静默改成有效任务。 |
| 图片 | PNG、JPEG、WebP、GIF、BMP、TIFF、AVIF、HEIC/HEIF 栅格图解码后转换为 PDF，修正方向、透明背景铺白、多帧转多页。 |
| PDF 文件 | 校验真实 PDF、非加密、有效页面；保留原始字节。 |
| 音频、视频、Word、Excel 及其他文件 | 整条拒绝，直接通过机器人发送文件问题提示。 |
| 损坏、空文件、超限附件 | 整条拒绝，提示具体附件并要求调整后重新发送。 |
| 钉钉 `unknownMsgType` | 保存可靠拒绝通知，提示改用文字、图片或 PDF；不下载、不初始化员工、不发布任务。 |
| 下载网络故障 | 不判断为文件不支持；接收未完成，不发布半条消息，等待钉钉重推。 |

先检查整条消息所有文件的类型和数量，再下载或转换。全部附件完成校验、可靠暂存后才进入待发布状态。单文件同样执行此流程。文件名只作提示，不参与磁盘路径；实际内容必须匹配允许的类型，不能只凭后缀接收。

钉钉可能将无法透传的消息回调为 `unknownMsgType`，格式见[官方接收类型示例](https://open-dingtalk.github.io/developerpedia/docs/learn/bot/message/)。解析器将其归一为无下载码的 `unsupported` 标记，由接收器写入 `reply_pending`，后台通过 OpenAPI 向发送者发送拒绝提示；Stream 协议 ACK 本身不是聊天回复。企业、机器人、单聊及发送者身份检查仍然生效；身份缺失或畸形回调继续失败，不猜测收件人。上游的未知类型说明不写入业务正文或模型上下文。

图片消息和富文本中的图片片段优先使用 `downloadCode`，缺失或为空时读取钉钉支持的 `pictureDownloadCode`；其他附件仍必须提供通用下载码。图文消息按片段顺序保留全部正文及图片，不能因部分解析失败而只发布文字。格式校验失败时，日志附带固定阶段标识和脱敏结构：消息类型、片段数，以及白名单字段是否存在；不输出正文、员工身份、下载码、文件名、未知字段名或回调地址。结构日志最多展示前 10 个片段，避免日志膨胀。没有可信下载码的图片仍明确失败，不将缺失图片的半条消息当作成功接收。

富文本中的空字符串和纯空白文字片段作为编辑器占位忽略，有效文字原文及附件相对顺序保持不变。仅图片与空白占位组成的消息按图片消息继续处理；全为空白且没有附件则失败。缺失 `text`、非字符串正文和未知片段仍拒绝，不借忽略空白放宽结构校验。诊断中的 `text_state` 只区分 `blank`、`nonempty`、`nonstring`，不记录原文；文字字段错误使用具体阶段，避免只打印 `invalid_message`。

提示示例：

```text
附件 2（budget.xlsx）：暂不支持该文件类型。本条消息未接收，请调整后重新发送整条消息。
```

提示通过 OpenAPI 直接发送，无须让助理生成一次回复。后台扫描默认在 3 秒内开始处理待发提示，网络不可用时按下文恢复策略处理，不保证发送成功等于用户已读。

可信 `senderStaffId` 在权威员工表中不存在时，使用与网页登录共用的 [EmployeeOnboardingService](../../../app/service/employee_onboarding.py) 初始化，然后继续接收原消息，无需先登录主页或重发。只接受已认证 Stream 中通过企业及机器人校验的员工 userid；不使用昵称、机器人传入的管理员标记或开发模拟资料替代身份。

初始化读取真实钉钉姓名、部门、头像、直属主管和职位，按现有规则为可见平台及自身赋初始文件权限 0，不赋管理员身份。已有员工直接使用 SQL 资料；网页登录和机器人共用初始化实例及 userid 锁，跨进程由员工主键保护。详细事务边界见[首次员工初始化](../../architecture/system/user-auth.md#首次员工初始化)。

整条附件类型及数量检查通过后才初始化，初始化提交成功后才下载附件和进入 `publish_pending`。钉钉、人员库、平台目录故障，或初始化依赖缺失时，上抛异常并保留 `received`，不确认接收、不发布任务，也不发送“先登录主页”的拒绝提示；后续同一消息重推重新检查，已建档部分不会重复覆盖。取消及超时遵循同一规则；初始化超时后不会脱离回调继续后台写入。`received` 不由后台扫描恢复，仍依赖钉钉重推或人工核对，不保证无限重推。

初始化只建档，不创建中央用户登录、不签发用户 token。助理消费者下一轮员工扫描会发现新员工，复用既有助理绑定和任务消费流程。

## 文件与队列

[转换器](../../../app/infrastructure/robot_attachment.py)在内存中处理字节，复用 Pillow 和 PyMuPDF，不启动外部格式转换程序。下载阶段兼容钉钉返回的 HTTP 标准 OSS 桶地址，升级为 HTTPS 后继续受原有域名和公网校验约束，详见[下载规则](../infrastructure/dingtalk-robot.md#附件与日志边界)。图片像素数、帧数和最终 PDF 字节数分别校验，禁止把动画静默截成首帧。

苹果 HEIC/HEIF 由 `pillow-heif==1.8.1` 注册到 Pillow 解码，文件附件接受 `.heic`、`.heif`、`.heics`、`.heifs`、`.hif`（不区分大小写），图片消息无需文件名。实际内容仍须通过解码和允许格式检查；解码器处理 HEIF 容器方向后，复用现有逐帧转换，不重复旋转，不把缩略图作为额外正文页。输出继续使用 PDF，无需修改队列、存储格式或模型工具。此转换用于读取静态图像，不提取 Live Photo 的视频部分。

依赖安装到实际运行环境后须重启后端；容器部署需基于更新的 `requirement.txt` 重建后端镜像。解码依赖及预编译包说明见[Python 环境与依赖](dependencies.md#heic--heif-解码)。

转换后的所有附件都以 `images` 引用、`.pdf` 后缀通过现有 [UploadFileStore](../../../app/infrastructure/upload_file.py)暂存到 `data/user/upload-file`。稳定 UUID 来自消息标识和片段位置；相同回调恢复时复用已保存文件。存储层拒绝路径穿越、符号链接及不同内容覆盖。入队前再次核对已冻结的大小和 SHA-256。

发布时使用同一个稳定 `request_id`、原文字正文和有序 PDF 附件列表；无文字的纯附件消息使用“请查看附件。”。发布协议复用[中间件队列客户端](../infrastructure/assistant-queue.md)，不另加消息类型、接口或队列。正文不包含下载码、追踪标识或存储信息。

中间件返回严格验证的成功回执后清理本地入站暂存文件；消费者领取时按任务账本重新可靠转存、关联节点，后续记忆命中仍可通过公共 Core `view_image_file` 查看附件。清理失败保留待清理清单，重试清理不重复发布任务。

## 接收账本与恢复

手工迁移 [014-assistant-robot-inbox.sql](../../../schema/014-assistant-robot-inbox.sql) 创建 `assistant_robot_inbox`，模型为 [RobotInboxRecord](../../../app/model/robot_inbox.py)，仓库为 [RobotInboxRepository](../../../app/repository/robot_inbox.py)。这张表记录 Stream 接收去重和未完成交付，不承担任务调度或优先级排序；助理任务队列仍由中间件维护。

| 字段 | 含义 |
| --- | --- |
| `request_id` | 企业、机器人及业务 msgId 导出的稳定主键。 |
| `userid` / `fingerprint` | 可信员工身份及输入一致性校验；同 ID 内容改变时拒绝。 |
| `message` / `files` | 冻结正文及计划/准备完毕的文件 UUID、大小、SHA-256；不保存二进制。 |
| `status` / `reply_text` | 接收、发布、拒绝通知和待核对状态；拒绝文案只保存用户可见的原因。 |
| `publish_started_at` / `next_attempt_at` | 首次尝试与下次重试时间，用于限制自动重放窗口。 |
| `created_at` / `updated_at` | UTC 时间。 |

| 状态 | 后续行为 |
| --- | --- |
| `received` | 附件准备尚未完成，不能成功 ACK；依赖 Stream 重推继续，不把缺少下载码的残留记录自动发布。 |
| `publish_pending` | 正文和全部附件已经可靠保存；后台发布。 |
| `publish_unknown` | 外部调用开始前先保存；网络异常、取消或回执落库失败后，窗口内使用同一冻结请求重试。 |
| `publish_blocked` | 明确请求冲突或重试窗口已过；停止自动发布，等待核对。 |
| `published` | 已验证中央接收；清理暂存附件，后续重推仅确认。 |
| `reply_pending` | 整条拒绝通知已保存，后台发送；明确未发送的故障可重试。 |
| `reply_unknown` | 发送开始前先保存；结果不确定时不自动再次发送，避免重复通知。 |
| `rejected` | 钉钉已受理拒绝提示；清理附件，后续重推仅确认。 |

`publish_unknown` 超过重试窗口的记录停止扫描并保留原状态待核对；不会换新请求 ID 再发一次。必须使 `ASSISTANT_PUBLICATION_RETRY_WINDOW_SECONDS` 小于中间件发布幂等回执保留期，且部署侧不能提前清理接收去重记录。

所有消息准备完毕或拒绝通知可靠落库后才向 Stream 返回成功。数据库、下载、转换暂存失败不会确认接收成功。接收不等待中央发布或模型生成，因此中央短期不可用不会迫使用户重复发送已经暂存的完整消息。

下载码只在当前回调内存中存在，不落库、不写日志；因此 `received` 残留不能宣称支持无条件离线恢复，仍需钉钉重推或人工核对。钉钉发送没有客户端幂等键，`reply_unknown` 也不能宣称恰好一次交付。

## 并发与生命周期

仓库复用既有 MySQL 命名锁实现，使用独立 `robot-inbox` 命名空间按消息 ID 串行，跨实例互斥。同一用户正在生成时仍可接收后续短消息，由中间件按既有契约合并；不拿助理执行用户锁阻塞新输入。数据库事务只用于状态保存，不跨网络调用。

锁连接丢失会取消当前处理。入站后台将每条处理隔离为子任务，单条故障不会停掉整个扫描器。文件写入和删除即使被取消也等待工作线程结束，再释放消息锁，避免旧线程与重推并发写同一文件。

`DINGTALK_ROBOT_CALLBACK_TIMEOUT_SECONDS` 是本项目单条接收处理的总预算，默认 10 秒，覆盖消息锁、员工首次建档和附件准备；用于防止慢网络或处理长期占用回调并发槽位。它不覆盖后续模型生成，协议 ACK 只有可靠暂存或拒绝通知落库后才成功。超时会取消接收，保留尚未完成的 `received`，不在回调之外继续建档或假成功；未来重推重新处理。首次初始化服务自身另有 60 秒上限，但机器人入口仍受更短的外层预算约束，不能把内部上限当成实际可用时间。部署可按正常接收耗时调整回调预算，仍需控制各步骤耗时及并发；本次未修改实际超时配置。头像压缩优化与已复现的首次建档超时见[头像下载与安全存储](../infrastructure/user-infrastructure.md#头像下载与安全存储)。

停机先关闭 Stream 并取消等待回调，再关闭入站扫描器，然后清理其他助理任务、队列和 HTTP 客户端。待发布账本保留，不清空中央队列。启动会检查 014 表；应用不自动执行 DDL。
