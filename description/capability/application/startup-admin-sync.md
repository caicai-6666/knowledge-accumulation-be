# 启动平台管理员全表同步

## 用途与职责

知识后端在启动阶段将权威 MySQL `platform_admins` 完整关联，以及 development 模式无冲突模拟身份的 `managed_platforms`，发布到中间件管理员全表。只增加启动全量镜像职责，不迁移 SQL 关系编辑、registry 的管理员 add/remove 增量维护、管理员鉴权或门户路由；不调用 `POST user/update`。

[MiddlewareUserSyncService](../../../app/service/middleware_user.py)复用用户注册协调器、组合根唯一维护锁、平台会话与 HTTP 客户端，只有一个启动任务。用户注册规则见[用户全表注册协调](startup-user-sync.md)，跨后端覆盖边界见[职责与运维状态](../../architecture/system/user-auth.md#中间件维护方授权与运维状态)。

> **自动启动：** MIDDLEWARE_USER_SYNC_ENABLED 已按用户要求移除。配置中间件接入后自动启动“用户表 → 管理员表”同步；无管理员独立开关，首次登录也可受控补用户登记。历史隔离验证与后续授权部署应分别记录，不能将启动完成等同中央发布成功。

## 数据源与合并

1. 用户阶段先完整读取权威员工表；SQL userid 重复拒绝发布；开发 userid 已在 SQL 时只采用 SQL 权限，不重复追加配置身份。
2. 管理员阶段调用仓库 `list_platform_admins()` 读取 SQL 关系，不使用员工展示对象的 managed_platforms 代替查询，不从文件权限等级推导管理身份。
3. development 模式再次查询开发 userid，确认其 SQL 存在状态与用户阶段一致。已落库时仅发布 SQL 关系，不合并配置 managed_platforms；未落库时拒绝 SQL 关联引用该模拟身份，然后补充配置管理关系。阶段之间身份数据源发生变化则拒绝发布，需核对后重启。
4. production 由 AuthSettings.simulated_user() 返回 None，不合并开发 userid、管理列表或权限；即使 SQL userid 与配置开发 userid 相同，也按真实 SQL 身份处理。
5. 校验平台代码、userid、字典及列表类型，平台内去重排序。一个 userid 管理两个平台，计两条关系。完整范围来自权威 SQL，不通过可见门户目录过滤隐藏平台。
6. 所有管理员 userid 必须在本进程已成功注册的用户集合中。管理员读取失败、非法数据或未知 userid 不发布空表；SQL 真正返回空关联时才允许按空对象的清空语义发布。

确认集合仅表示用户登记状态，不存另一份权限或管理员缓存。SQL 新增管理员用户若尚未登记，管理员阶段失败重试并等待已有显式用户注册机制完成登记，不因该错误反复替换用户表。模拟配置不能覆盖真实员工或写 SQL 管理关系。

## 外部调用契约

使用知识后端自己的平台 `Authorization: Bearer <platform-token>`：

```text
POST /middleware-service/api/platform/admins/full-table
```

精确请求示例：

```json
{"admins":{"knowledge-accumulation":["employee-a"],"registry":["developer","employee-a"]}}
```

仅含平台代码及 userid，不发送姓名、头像、部门、文件权限或用户 token。接口省略的平台管理员会被清空，空 admins 对象清空所有已配置平台的管理员，因此完整数据范围必须先核对。

成功必须为 HTTP 200，响应为：

```json
{"admin_count":3}
```

`admin_count` 是严格非负整数，必须等于提交映射内去重后的关系总数；布尔值、字符串、缺失/额外字段、错误数量、非 200 或重定向均拒绝。请求与响应 DTO 见 [PlatformAdminTable / PlatformAdminTableResult](../../../app/model/platform_admin.py)，适配见 [MiddlewareClient.replace_platform_admin_table](../../../app/infrastructure/middleware.py)。HTTP 继续禁用环境代理与自动重定向。

## 两阶段编排与首次登记

启动后台等待已有平台 token，不提前查询数据库。取得同一 maintenance_lock 后：

1. 用户表尚未确认时，读取完整员工快照并发布用户 full-table，严格校验 count，再记录用户登记集合。
2. 读取并合并管理员全表，校验身份和登记依赖，发布管理员 full-table 并严格校验 admin_count。
3. 两阶段均成功后退出启动任务，不周期发布。`initialized` 仍只代表用户阶段，`startup_complete` 代表用户和管理员阶段都已成功。

前台首次登录若先完成用户登记，启动任务复用该确认，跳过重复用户发布，再做管理员阶段；若启动任务先持锁，显式登录等待。整个管理员读取与发布也持有同一锁，普通 token 查询不取维护锁、不写管理员表。正常显式登录只绑定新 token，不发布管理员表；后续按需用户登记也不重发已成功的管理员启动全表，后续管理关系编辑归 registry 增量流程。

管理员同步独立于普通用户登录成功与否，不能作为每次登录或 me 的隐式授权补写。中央随机 token、无本地映射/固定 TTL、verify 移除、头像读取等契约不变。

## 失败、超时与关闭

| 场景 | 行为 |
| --- | --- |
| 用户阶段失败 | 不进入管理员阶段；后台重读并重试用户阶段。 |
| 管理员 SQL、校验、网络、403、count 或超时失败 | 保留成功用户阶段，仅重读管理员关联并重试管理员发布，不重发用户表。 |
| 管理员关系尚无用户登记确认 | 不发送管理员表，不反复覆盖用户表；等待合法首次登记或用户处理源数据范围。 |
| 管理员请求 401 | 只失效该请求实际使用的平台 token，等待现有平台会话恢复，不创建第二个平台登录任务。 |
| 成功 | 启动任务退出；重复 start 不重复发布。 |
| 停机取消 | 取消并等待当前任务，释放维护锁；不发布清理空表，不删除中央关系。新应用实例可重新启动完整同步。 |

每次尝试继续使用 `MIDDLEWARE_USER_SYNC_OPERATION_TIMEOUT_SECONDS`（默认 30 秒），覆盖锁等待、尚未完成阶段的 SQL 与 HTTP；失败间隔使用 `MIDDLEWARE_USER_SYNC_RETRY_INTERVAL_SECONDS`（默认 30 秒）。管理员阶段重试使用新读取的关系而非缓存载荷；超时不能假定上游未提交，两个 HTTP 阶段也不是原子事务。日志仅输出异常类型、HTTP 状态码或成功计数，不输出密钥、token、原始响应。

## 授权与生产前提

用户已确认中间件完成适配，不再因旧授权等待而关闭装配；实际部署仍由用户负责。知识后端始终使用自己的平台身份，失败明确记录并重试，不借 registry 凭据。本方没有修改或调用中间件、registry、deploy、前端或共享服务，也不将“用户确认已适配”宣称为本方完成了真实联通测试。

真实启用前由用户确认最终授权、停止旧启动管理员发布方、完整管理员范围及人员先登记的依赖。两边必须读取同一权威 schema 的 employees/platform_admins，registry 后续增量维护须先持久化权威源；当前知识后端默认数据库名不证明已经同源。

同一进程锁只能协调知识后端内部：旧管理员快照仍可能覆盖 registry 刚完成的 add/remove，正如旧用户表可能覆盖新权限。源读取到中央提交之间的跨后端一致性，需要用户协调端到端版本拒绝或覆盖整个区间的串行契约。本轮不引入分布式设施，不宣称风险已解决；自动启动同步不代表上述跨后端竞态已由本进程解决。

## 隔离验证

新增[管理员启动同步测试](../../../tests/test_admin_sync.py) **21 项**，覆盖 SQL/模拟合并、两阶段顺序、生产不合并、阶段间身份冲突、真实空表与故障区别、管理员失败/401/403/超时恢复、取消与新实例启动、前台登记复用、未知关联不重写用户表、共享锁交错、普通查询不写、精确 DTO/Bearer/计数及重定向拒绝。

完整回归 **149 项通过**，保留此前 128 项中央 token、无 AUTH_ENABLED、头像、用户注册、9 项维护锁及 RSA 验证。全部 HTTP/SQL 用隔离 Mock，文件仅使用 tests/tmp；未读取真实头像或数据库，不把运行配置授权或生产联通列为已验证结果。

协作方此前独立通过的 20 项是新增未知关联重试测试前的快照；最终管理员专题数量以 21 项、完整 149 项为准。

移除注册开关后的当前完整回归为 **166 项通过**；管理员专题仍为 21 项。启动默认执行、无维护开关，SQL 冲突/错误、严格计数、两阶段重试和普通查询不写的语义保留。
