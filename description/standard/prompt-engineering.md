# 提示词工程规范

## 任务、事实与模型视角

提示词明确任务目标、输入、可用工具、输出、失败边界及简短示例。通用助手不预设合同场景；证据不足时说明限制或通过最终输出请求澄清，不编造资料、工具结果或权限。

模型可见文本只包含业务所需信息。禁止注入提示词版本、内部节点和树编号、运行 ID、工作流拓扑、缓存、调度或追踪元信息。版本和原始审计保存在模型上下文之外。本规则优先于参考项目版本标识要求。

---

## 稳定前缀与注入

系统角色、工具规则、工作区定义使用稳定组件。按确定顺序渲染，相同输入得到相同文本。用户资料、历史摘要、当前工作区及本次问题作为明确分隔的数据注入，不从用户文本中解释 system/tool 等角色，不将引用的反馈标签提升为系统指令。

平台等级必须由已认证身份提供，模型提示不替代权限校验；缺少平台键不表示默认零或获准访问。思考强度使用经过校验的生成配置，分词与生成使用相同配置。

---

## 2.5 工具参数描述

每个模型可见函数工具参数，包括嵌套对象和动态属性，都在实际 JSON Schema properties 字段上提供非空且准确的 description。说明业务含义、来源、范围和空值语义；字段名、docstring 和总体工具描述不能替代字段说明。动态字典须在 additionalProperties 的值 Schema 中说明条目的含义。

注册时和测试中递归检查 definitions、properties、items、anyOf 及 additionalProperties。工具 Schema 与执行参数模型来自同一注册项，拒绝重复名称，未知字段拒绝。

工具说明借鉴 contract-service-be：先用“当你需要……时，使用这个工具”说明使用时机，再说明一次调用做什么、返回什么，以及成功后继续还是结束。只保留会影响模型选择或正确调用的失败边界，不把内部执行流程写成工具使用说明。

字段说明应直接告诉模型去哪里取值、如何填写、范围及省略或 null 的含义；有歧义时给一个短例子。例如图像页码明确“按文件顺序，从 1 开始；上次看第 3 页，省略则看第 4 页，重看第 3 页需填写 3”。来源名称必须与实际上下文渲染一致，本项目附件使用“文件ID”，不能照搬参考项目的“内部索引”。

借鉴写法时必须对应当前实现：不复制合同工具、未实现的业务流程、参考项目容量百分比或内部调度说明。检查最终生成的工具定义与字段 Schema，不能只修改未被注册使用的注释。纯说明修改也应确认名称、类型、必填项及执行边界没有变化。

## 协议与验证

每次仅接受一个完整原生工具调用。原生调用旁可附带普通说明，程序按实际工具及参数验收；普通文本本身、多工具、拒绝、截断、未知工具、非法 JSON、重复键和非有限数字均不得作为动作。附带说明仅保留私有审计，成功轨迹使用规范化工具对。不能从普通文本或 Markdown 提取伪工具调用。只在协议、参数、状态和业务全部校验通过后提交。

反馈仅描述字段位置、问题及可执行修正，不回显无效正文、敏感输入、异常堆栈或工程标识。纠错有明确次数上限，成功后清理整个失败链，遵循[上下文规范](agent-context-management.md)。

对外输出使用中途和最终输出工具，不直接展示原生推理。原生推理及所有失败响应完整保存到私有生成记录，无轮数窗口；是否注入后续上下文是独立策略。

---

## 定向纠错与失败处理

反馈必须匹配产生问题的阶段，提供已注册工具、受控字段位置、具体约束、可执行的修正方向以及已确认的执行状态；不能把不同失败都压成“检查参数”，也不能直接回显异常原文或无效输入。仅模型能修正的调用错误消耗模型纠错次数；正常结果、权限限制、依赖故障和执行结果不明分别处理，程序恢复须有独立有限预算。

没有后续模型请求的终止分支不能靠追加system-guidence完成通知；宿主须记录真实状态并可靠通知用户，结果不明先核对，不自动重放副作用。具体修复提示遵循[项目开发规范第8条](../../AGENTS.md#代码要求)，在校验或失败分支就近维护。公共 system-guidence 构造器只负责包装，结构化异常只传递校验处提供的安全文本；Schema 格式化只读取可信字段与约束，不回显输入、异常原文或未知属性名。修改规则时同步修改相邻反馈，并检查下一轮实际请求及成功后的清理。

审查证据、代码位置与尚待实施的失败处理见[失败反馈审查](../architecture/workflow/question-answering/error-feedback.md)，该文档不再维护业务提示文案目录。
