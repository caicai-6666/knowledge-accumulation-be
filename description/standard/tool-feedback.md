# 工具反馈渲染规范

## 适用范围与当前状态

本规范定义工具执行后模型应该看到什么，适用于个人助理、探索模式及内部子智能体的成功、空结果、失败、无变化和等待反馈，也适用于宿主使用 `user` 消息传递的工具纠错提示。具体原因与修复动作遵循[项目开发规范](../../AGENTS.md)的就近维护要求；轨迹生命周期遵循[多轮上下文规范](agent-context-management.md)。

> **强制契约：** 程序消费结构化结果，模型阅读经过程序渲染的业务正文。二者职责必须分离，不能把内部结果对象序列化后直接作为模型反馈，也不能把已排版文字再包入 JSON 字段。

本规范不改变模型调用工具时的 JSON 参数 Schema，不改变 HTTP API 的 JSON 契约，也不禁止模型在独立生成任务中按 JSON Schema 输出。业务资料本身需要展示 JSON 或代码时，可以作为明确标注的资料呈现，但不能用它替代执行状态与错误反馈的渲染。

**当前内置工具已完成迁移。** Core 的 20 个具体工具、最终输出历史回执、探索 `emit_progress` 及个人助理 19 个专属工具均已接入独立末尾渲染钩子，内部检索与整理工具循环也已覆盖。旧历史和兼容注册项保留 JSON 回退，不要求改写历史数据。[工具迁移清单](../architecture/workflow/question-answering/tool-content-contract.md#模式专属工具反馈清单)记录具体范围与验证边界；此结论不覆盖外部提供方托管的工具。

## 程序结果与模型正文分离

| 内容 | 责任与用途 |
| --- | --- |
| 结构化执行结果 | 服务和仓库确认的状态、业务字段、错误类型、动作回执等，用于程序分支、事务、幂等及必要的持久化。 |
| 模型可见正文 | 从已确认结果中选择当前任务所需的信息，使用业务名称和可读排版，供模型理解结果及决定下一步。 |
| 权威业务状态 | 数据库、已提交工作区等实际状态；不能以渲染文本、模型复述或普通生成内容替代。 |
| 私有审计 | 原始生成、拒绝事件、工程追踪信息；按既有审计要求保存，不直接注入模型正文。 |

业务字段和展示文字应来自同一次执行结果，不能为渲染重新执行查询或副作用，不另建模型转换调用推测执行事实。公共层可以复用结果信封和排版能力；具体业务字段、错误原因与修正方向仍由对应工具或校验分支维护，禁止新增集中式业务文案表。

不得从模型可见文本反解析业务字段来执行数据库写入、权限判断或幂等判定。既有程序若依赖 JSON 工具历史，必须先设计并落实独立的结构化消费路径，再调整展示。

## 渲染钩子设计

后续新增或改造工具，统一将最终反馈正文的生成放在该工具独立注册的程序渲染钩子中。各工具的钩子链彼此隔离；可复用无业务语义的排版函数，但不得将所有工具的业务文案集中到全局分发器。

- 渲染钩子位于该工具业务钩子之后，作为钩子链最后一步，使用本次执行及前置钩子已经确定的结果生成正文；随后由 Core 完成校验与相应提交，再按原有规则将反馈交给模型。提交失败时不得发布成功回执。
- 渲染钩子只设置展示内容，例如普通反馈的 `OrdinaryToolContent.text`，保留结构化业务字段、执行状态、提交回调和幂等语义；不重新查询、不执行副作用、不调用模型猜测结果。
- 具体错误原因、执行状态和修正动作仍由产生条件的校验或业务分支就近提供。渲染钩子仅排版这些信息，不自行推断原因，也不将上游定向反馈泛化。
- 成功、空结果、无变化和可纠正失败都必须覆盖。若当前钩子仅在成功路径运行，改造时必须补齐失败结果的渲染路径，但不能因此让失败结果执行仅适用于成功的业务钩子。执行前的 Schema 或预演拒绝继续由原校验路径提供可读反馈，不为排版强行执行工具。
- 可折叠工具分别处理轻量回执与资料正文，保留原资料解析和分页能力。结果不确定、异常及其他终止分支继续遵守原终止规则，不为发送渲染正文而新增下一轮模型请求或重放动作。

这是后续设计约定，不代表现有工具均已接入渲染钩子。已有执行器内直接渲染、旧 JSON 回退及内部子循环，随对应工具逐项迁移；工具反馈渲染与 `finish_task` 最终答案的业务转换钩子职责不同，不替代后者。

## 模型可见格式

反馈正文直接使用可读文本或轻量 Markdown，短结果优先采用“标题＋中文字段”，并根据内容使用列表或表格。标题说明本次操作；字段名、业务术语与工具说明保持一致。不为短回执引入额外页面或复杂层级。

源码中的固定反馈正文使用可直接审核的多行文本模板，让标题、空行和字段排列与实际输出一致；需要插值时使用多行 f-string，通过 `dedent(...).strip()` 去除代码缩进和首尾空白。避免把整段反馈写成包含大量 `\n` 的单行字符串或逐行字符串拼接。动态可选字段可单独追加；业务原因与修正动作仍在原校验分支维护，不能为模板展示迁移到集中式文案库。修改构造方式时应验证实际输出的空白和正文不变。

- 不直接展示 `{"status":"accepted"}` 等原始机器对象；仅“已接受”不能代替业务上究竟完成了什么。
- 不使用 `{"message":"标题及排版正文"}`、`{"text":"..."}` 等 JSON 外壳冒充友好渲染；模型实际收到的正文须是渲染结果本身。
- 不额外包围整个短反馈为代码块。文档示例的代码框只用于展示格式，不是工具正文的一部分。
- 保留后续调用需要的完整业务标识，如文件 ID、任务 ID、查询 ID、响应 ID，不能用缩写、页内序号或展示名称代替。
- 时间说明时区，数量说明对象，页码说明范围；根据工具用途显示必要字段，不为统一模板塞入无关字段。
- 不重复工具描述中已有的固定能力说明，不无条件追加“说明”“注意”等段落。只有影响本次结果判断或下一步选择的限制才进入反馈。
- 错误码、堆栈、运行 ID、请求追踪标识和内部调度信息留在程序或审计中，不能以方便调试为由注入模型。业务上确有后续用途的标识与工程追踪标识必须区分。
- 外部名称和正文作为资料处理，必要时转义控制符或使用清晰的资料边界，避免伪造反馈字段、角色或程序指令。

工具参数与原生消息仍遵循模型接口协议；本规范要求的是反馈 `content` 的阅读格式，不是取消 `role`、`tool_call_id` 等协议字段。

## 成功、失败与不确定状态

| 情况 | 模型反馈要求 |
| --- | --- |
| 查询成功 | 明确查询成功，展示必要结果、来源业务标识及适用范围。 |
| 修改成功 | 仅在相应提交已确认后说明成功，展示确认后的关键字段；不能把预验、排队或提交中描述为完成。 |
| 无变化 | 明确“已是目标值，无需修改”，不声称产生新变更，不伪造更新时间。 |
| 空结果 | 明确查询已完成且没有匹配项；按需给出调整条件的方向，不能把依赖故障伪装为空。 |
| 等待或超时 | 说明实际进度及是否已发送、是否仍有可等待结果；返回已确认有效的继续等待标识，不诱导重复发送。 |
| 明确失败 | 展示具体原因、已确认的执行状态和可执行下一步；不同原因分别判断，不能拼接一串可能原因让模型猜测。 |
| 结果不确定 | 不声称成功或“没有修改”，不自动重放副作用；恢复时按工具契约核对权威状态。 |

失败提示必须与程序确实知道的事实一致。例如数据库中没有上传登记，只能说“未找到登记记录”，不能推断原文件不存在；若已明确检查出归属不符，应返回对应权限原因和操作方向，不夹带其他业务的修复说明。涉及访问控制时仍须遵守该工具明确的披露边界，不泄露他人的身份、私密内容或其他无关资料。

修正方向必须可执行：指出应核对哪个业务 ID、修改哪个参数、重新查询什么，或交由哪个有权限的主体操作。若模型没有补登记、恢复服务等能力，应明确需要相应主体或流程完成，不能暗示存在未提供的工具。

执行状态由程序控制，渲染器不能把失败改成成功、把不确定改成未执行。终止分支没有下一轮请求时，反馈对象存在不等于模型收到提示；`finish_task` 等成功后结束循环的工具也不能被描述为“下一轮模型已看到成功回执”。

## 可折叠资料与错误恢复

可折叠工具有两个独立展示责任：轻量工具回执说明本次查询或阅读状态、必要标识及分页信息；资料消息展示正文、表格或图片。已有资料页排版不意味着 JSON 回执符合规范，回执、空结果和失败分支仍须分别改造。

保留原有资料引用、授权校验、展示窗口、分页提交和过期语义，不能为了反馈排版将大段资料塞入普通回执，也不能把程序内部资源标识或展示轮数暴露给模型。

可纠正失败的调用和反馈只在连续纠错期间进入模型上下文；后续动作完整成功后，清除整段失败轨迹，保留私有审计。下一轮必须使用具体分支提供的修正提示，不能被下游捕获逻辑泛化。正文样式变化不改变是否允许重试、继续等待或终止的规则。

## 示例

示例仅展示格式，不要求其他业务复用这些字段或文案。文件 ID 和时间为示例值。

```text
### 文件可见范围查看

状态：查询成功
文件 ID：12345678-1234-1234-1234-123456789abc
可见范围：私密（private）
文件上传时间：2026-11-08T02:00:00+00:00
元信息更新时间：2026-11-09T08:00:00+00:00
```

```text
### 文件可见范围修改

状态：修改失败
原因：该文件不属于当前所属用户，无权修改可见范围，本次未修改。
下一步：请由文件上传者的助理操作；如选错文件，请改用所属用户上传的文件 ID。
```

## 逐项改造与验收

每次优化一个工具或一组明确关联的工具，应完成以下检查：

1. 追踪注册项、执行器、执行后钩子、公共渲染、资料展示、持久化和历史恢复，覆盖主 Agent 与子智能体实际使用的路径；不能仅凭 Python 返回 dict 判断模型看到的格式。
2. 列明成功、有数据/无数据、无变化、参数错误、权限拒绝、依赖故障、超时及结果不确定中实际存在的分支，明确各分支已确认的执行事实。
3. 核对是否有事务钩子解析工具历史中的 JSON、按结果字段提交业务动作或恢复幂等状态；先保证结构化结果独立可用，不破坏事务原子性、重试和旧数据恢复。不得直接将这些程序依赖的回执字符串替换为展示文本。
4. 核对每个工具独立注册的末尾渲染钩子及成功、失败路径覆盖，优先复用公共能力。当前普通工具可以使用 `OrdinaryToolContent(text=...)`，可折叠工具可以使用 `FoldableToolContent(feedback=FoldableReceiptText(...))`，由钩子提供展示、隐藏和不可读三种正文；`view_memory_query` 已接入。其适用边界、历史保存及旧 JSON 兼容机制见[Core 返回契约](../architecture/workflow/question-answering/tool-content-contract.md)。可折叠工具和内部子循环须检查各自真正的消息构建路径，不能只改普通渲染器。
5. 检查传给模型的实际 messages：成功及错误正文已经可读，没有 JSON 外壳、无意义重复说明、私有字段或异常原文；需要的业务 ID、时间和分页信息完整。计数与生成使用同一份展示内容。
6. 验证可纠正反馈实际到达下一轮，成功后失败轨迹全部清理，私有审计仍在；终止分支检查没有自动重放，不声称模型已收到未发送的提示。
7. 验证业务结果、权限、提交与历史恢复未因展示变化而失效；提供给用户审核的反馈样例必须与程序实际输出一致，并同步工具专题文档。

现有 JSON 回退仅服务于尚未迁移的工具与历史兼容，不作为新工具继续直接返回 JSON 的默认选择。每次报告应明确本次覆盖的工具与分支，不能将部分工具通过验证表述为全部工具已符合规范。
