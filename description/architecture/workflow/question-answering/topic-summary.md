# 主题发现与工作记忆总结

将 contract-service-be 的主题规划、按主题生成和完整汇总迁入公共 Core，供任务前树摘要与任务内上下文整理共用。树的选择与容量触发仍由[树状上下文管理](context-management.md)负责；本模块不读取数据库、不选择其他分支、不执行业务工具。

---

## 处理流程

1. 将当前路径的最近摘要作为旧记忆，将FIFO选定的完整历史前缀按时间顺序编号为本次来源 `task_1` 等。本轮活动任务不参与摘要。按可信 `source` 过滤程序操作指导，保留真实工具结果和用户引用的同名标签；去除私有推理和未过滤的预渲染缓存，只处理副本，不改原计数和审计。失败轨迹由执行器在动作成功后清除，摘要器不按正文猜测失败。
2. 规划模型通过 `extract_topic` 增量选择主题，以 `finish_topic_planning` 结束。新主题追加，同标识完整替换且保持顺序；最多32个主题、96轮，连续错误上限复用 Core 配置。
3. 每个主题只获得自身选中的旧主题和任务副本，并行生成 `current_memory` 与 `open_items`。生成通过 JSON Schema 约束，不开放工具，不允许模型重写主题身份、标题或添加 reasoning 字段。
4. 检查结果集合与规划精确一致，校验身份、标题、引用和总容量，按规划顺序汇总。全部成功后才返回供调用方提交；失败不返回部分摘要。

使用 `asyncio` 实现 plan/map/reduce，与本项目既有异步子 Agent 接口一致；没有新增后台任务或重复的 LangGraph 宿主。并发额度复用 MLLM 客户端的共享限制。任一生成失败或外层取消会取消并等待所有未完成分支。

工作区精简与主题总结分开：达到工作区预算时进入[多轮编辑循环](workspace-compression.md)，以 `finish_compression` 显式结束，不再一次提交完整 workspace。组合整理先验收工作区、随后生成主题摘要，两者都通过后才提交。单纯工作区操作溢出时不触发主题总结。

## 记忆与来源契约

| 对象 | 字段与规则 |
| --- | --- |
| 主题规划 | `topic_id`、`title`、`scope`、`task_ids`、`previous_topic_ids`。至少一种有效来源，引用不得重复或悬空。 |
| 单主题输出 | 仅 `summary.current_memory` 与 `summary.open_items` 两个列表。 |
| 记忆条目 | `content`、`task_ids`、`sources`；任务引用只能来自分配的当前资料，旧记忆独有内容允许空任务引用。 |
| 汇总结果 | 程序填写主题身份与标题；结果必须与规划一一对应，不允许缺项、重复或额外主题。 |

主题按继续工作的价值筛选，允许合并、拆分或舍弃旧主题，也允许零主题。不强制每个任务有归属，不因未出现新进展丢弃仍有效的约束。旧主题必须被显式选中才会保留；空规划成功后不会隐式恢复旧摘要。

`scope` 是简短提取范围，不是事实依据或新增任务。全局目标与偏好有价值时集中为全局主题；其他主题不复活已被替代的旧要求。总结保留必要条件、来源、不确定性、暂停/取消/调整方向及失败语义，不将工具调用发出当成业务成功，不把检索未命中扩大为外部信息不存在。

来源标签只在当前整理输入内有效，不是数据库节点 ID。旧摘要中的任务标签不会再次作为当前来源注入。`sources` 由模型保留已有可定位出处；代码可以验证结构和引用范围，不能自动证明自然语言语义与来源完全一致。

## 存储与注入

继续使用 `SummaryContent.text` 与任务内 `context_summary.text` 字符串承载内部序列化结果，不新增 SQL 列。新值是严格结构的 `{"format":"topic_memory","topics":[...]}`；结构摘要的覆盖起止节点由既有树字段记录；运行内部分摘要使用 `covered_turns` 保存精确前缀范围，恢复规则见[上下文管理](context-management.md#预算与压缩)。这些覆盖元数据不放入模型材料。

主模型注入及打开探索树的公开 `content.text` 均投影为可读业务正文，隐藏格式标记、主题标识及本次来源标签。打开树不会修改存储中的结构。历史纯文本摘要保持原样展示；再次整理时明确作为一个旧记忆来源，不能虚构其内部主题或出处。已识别为新格式但内容损坏时明确失败，不静默降级成普通正文。

模型实际看到的摘要正文示例：

```text
### 交付状态

#### 当前记忆

- 交付已确认，但验收尚未完成。
  来源：交付凭证

#### 未决事项

- 等待用户确认验收结果；暂不推进下一阶段。
```

外层仍使用[历史摘要边界和安全围栏](context-rendering.md#本项目的数据边界)。S1 → C → D → S2 → E 中，从 D 整理只处理 S1、C、D，形成新 S3；不读取 S2 或 E，不改变既有分支和工作区快照。

## 预算、纠错与私有审计

模型请求与结果验收使用同一 vLLM 分词器。每个规划/生成请求保留配置的输出额度，并检查输入加输出预留不超过模型窗口；单主题不再按主题数平均分配容量，也不因超过平均份额而重试或删除信息。各主题可按实际信息量使用不同篇幅，最终对完整渲染后的摘要执行总容量校验。总量达到或超过目标时本次整理失败，不截断内容、不提交部分摘要；结构及引用错误仍有界纠错。超大输入的分段分层整理没有在本次新增。

规划可以有分析轮，但普通文字不会提交主题。合法工具动作后清除临时分析和整个错误反馈链；原生推理仅保留在私有审计，不重注入。总结 JSON 失败仅反馈最小修正要求，不把坏输出变成事实来源。

内部工具反馈同样遵循[工具反馈渲染规范](../../../standard/tool-feedback.md)。工作区精简循环的三个编辑工具各自注册副本专用末尾钩子，正文采用可直接审核的多行模板，展示“修改成功，仅更新整理副本”、实际编辑位置和容量；不沿用主助理的宿主提交成功语义。位置与容量由原验收、计数流程提供，钩子不重做编辑，候选计数或渲染失败不进入下一轮。

`extract_topic` 注册独立末尾渲染钩子，成功正文说明“主题选择已接受”，不声称主题摘要已生成。规划请求保留最近一次成功调用的规范化 assistant/tool 对，旧成功回执被新回执替换，权威主题集合仍逐轮以 YAML 重建；拒绝事件仍由原业务校验分支就近提供可读修正信息。新钩子仅排版，不改变来源校验、主题数量限制或主题替换规则。

`finish_compression` 与 `finish_topic_planning` 验收成功后直接返回，没有下一轮成功回执；校验拒绝时仍走各自原有纠错分支。主题正文生成是无工具的 JSON Schema 输出，不属于工具反馈，不改其机器协议。主助理回执改造不代表子智能体自动达标，必须分别验证这些内部路径。

新增[内部链路反馈测试](../../../../tests/test_compaction_internal_feedback.py)从 Core `_compress` 调用真实整理编排，使用模型与计数替身，检查工作区及主题规划的下一轮可读反馈、成功后错误轨迹清理、7 次原始生成审计保留、原工作区不变及未提前提交。未调用真实模型或验证数据库持久化。

所有规划、总结和工作区调用均由 Core `_invoke` 记录完整响应和流式分片，沿用原有 `history_summary`、`context_compaction`、`workspace_compaction` purpose。模型调用并行，`record_generation` 使用本次整理专用锁串行保存，避免 NodeJournal 检查点 revision 冲突；锁不串行整个生成请求。取消与故障沿用已有有界清理规则，不承诺故障数据库一定能够保存审计。

复用 `max_consecutive_errors`、MLLM 上下文/输出额度及并发配置。vLLM 需要支持 Chat Completions 的 `response_format.json_schema`；不支持时明确报错，不自动退回无约束输出。

## 摘要独立生成配置

主题发现与按主题总结统一使用 [sampling.py](../../../../app/agent/core/subgraph/context_management/topic_summary/sampling.py) 的参考采样参数：

| 参数 | 摘要值 |
| --- | --- |
| `enable_thinking` | true |
| `temperature` / `top_p` / `top_k` | 1.0 / 0.95 / 20 |
| `min_p` | 0.0，实际写入 vLLM 请求 |
| `presence_penalty` / `repetition_penalty` | 0.0 / 1.0 |

推理强度、输出额度及seed来自服务构造时加载的 MLLM 配置快照：`VLLM_MLLM_REASONING_EFFORT`、`VLLM_MLLM_MAX_COMPLETION_TOKENS`、`VLLM_MLLM_SEED`。不新增摘要专属开关；配置强度支持 low、medium、xhigh，模型模板映射沿用[统一模型配置](../../../capability/infrastructure/vllm-models.md)。

主任务仍按用户请求选择思考档位。Core 为摘要单独传入 `self.settings.generation`，不使用该请求覆盖后的 generation；任务前 `history_summary`、自动/主动 `context_compaction` 走同一入口。分词与生成使用同一份摘要参数。摘要始终启用思考，即使主任务关闭思考或选低档，也不影响摘要配置；不修改主任务参数及共享配置对象。这里只调整主题规划和总结，不改变独立工作区编辑循环的参数策略。
