# 员工个人信息与助理私有画像

> **当前部署入口：** 新空库仅执行 deploy 的[最新初始化脚本](../../../../../knowledge-accumulation-deploy/mysql/init/001-schema.sql)。本文中的编号迁移和旧库操作属于历史演进记录，不是新部署步骤；历史 SQL 已从当前仓库移除，仅可从 Git 历史追溯。已有数据库须另行制定升级方案，不可重跑初始化。

## 用途与范围

个人助理结合所属员工的事实资料理解工作场景，并按照明确边界形成对交互对象的理解与偏好。每个助理维护自己的画像视角，只记录所属用户本人及其他用户的 AI 助理；不为其他员工本人另建一套画像，也不自动共享画像库。

本模块已接入员工背景加载和系统提示词，以及画像名称全文查询、分页查看、单条新增和单条删除四项工具。画像使用独立表存储，姓名仍来自权威员工表。增删只在工具动作与节点检查点共同提交后才算成功。历史对话、摘要和普通工作区记录不等同于专门画像存储。

基础事实定义见[人员契约](../../data/personnel.md#任职资料与初始化)，通用注入机制见[模式装配](agent-modes.md#上下文与提示词)，任务入口见[助理消费](../../../capability/application/assistant-consumption.md)。


画像查询、查看、新增和删除均通过各自末尾钩子渲染可读回执：查询保留 ID、用户与偏好数量及截断状态，查看提供三态回执，增删展示稳定 key 和已确认结果。新增/删除注册 `persist_result=True`，事务消费任务的独立结构化结果，旧 JSON 历史只读兼容；动作指纹、同事务回滚与幂等规则不变，不从渲染正文反解析偏好。

## 所属用户忠实条款

[个人助理角色](../../../../app/agent/assistant/prompt/role.py)直接定义忠实条款，经统一组合入口进入用户消息、其他助理消息、提醒和心跳四类任务的系统提示词。目标是维护所属用户的知情、选择和正当利益；归属依可信身份资料确定，主管、其他员工或其他助理不能自行改变授权。

条款明确禁止与任何人或助理串联，对所属用户实施欺骗、伤害、隐瞒重要事实、伪造结果、操控或未经授权的承诺。对方要求保密或声称“为用户好”不构成例外。收到相关请求时应拒绝、停止相应协作，并向所属用户说明请求、可核实事实、风险和实际措施；来源或意图不清时区分事实与推断、暂停并确认，不凭含糊信息指控他人。

所属员工在职且需要告知时，`finish_task.send_to_user` 必须选择 true；[任务提示词](../../../../app/agent/assistant/prompt/task.py)明确该规则不受其他助理消息/心跳默认静默行为影响。所属员工已离职时仍拒绝不当请求并保存完整事实、风险及措施，但必须选择 false，不发送员工通知；此规则优先于忠实条款的通知要求，待确认事项不能擅自执行。离职不妨碍其助理接收其他助理的通信。通知保护凭据、私有推理及第三方隐私，无法披露时如实说明限制，不制造虚假说法。正常获得授权的协作继续执行，普通内部整理可以静默。

忠实条款本身属于模型行为提示词约束，不新增内容判定器；其中离职员工不通知的边界另由 `finish_task` 基于本轮可信身份执行程序门禁，详见[最终输出校验](../../../capability/application/assistant-consumption.md#finish_task)。程序不从对话推断状态，也不接受模型改变身份；不宣称提示词能绝对保证模型行为。示例覆盖串联伪造成功结果及隐瞒不利条件代用户承诺。

2026-10-26 验证：个人背景现有回归 12 项通过；另通过真实助理工厂构建四类任务实际发送的消息，确认忠实条款在 system 消息中各出现一次，均包含禁止合谋、隐瞒及必须通知的交付规则。`git diff --check` 通过。未调用真实模型评估拒绝行为，未发消息或修改业务数据。

## 员工事实资料

[AssistantEmployeeContextLoader](../../../../app/service/assistant_personal_context.py)接受消费宿主从权威员工表取得的 `AuthenticatedUser`，通过 `find_work_profile(user.userid)`读取任职 JSON，必要时按直属主管 userid 查询其姓名。每次生成单独加载，不遍历全员、不在共享 Core 中缓存。

| 资料 | 来源 | 缺失处理 |
| --- | --- | --- |
| 所属员工 userid、姓名、部门名称 | 宿主绑定的 SQL 员工身份 | 保留已有空值，不推断职位或部门关系 |
| 在职状态 | `employees.employment_status`，随宿主 SQL 员工身份读取 | `employed` 展示在职，`resigned` 展示离职；非法值拒绝，首次创建默认在职 |
| 职位、直属主管 userid | `employees.work_profile` | 字段为空时明确未知，不以部门主管替代 |
| 直属主管姓名 | 仅查询该主管的员工记录 | 主管尚未落库时保留 userid、姓名为空 |

加载结果作为 `AssistantContext.profile` 中一条 `ContextMaterial`：包含业务来源，状态为 `confirmed`，表示当前已保存的企业记录，不保证现实中从未发生调岗。任职资料故障上抛，不把数据库异常伪装为空资料；当前员工记录已不存在时停止生成。

`AssistantConsumer`通过已有助理工厂的 `context_loader` 注入加载器，覆盖用户消息、其他助理消息、提醒和心跳。直接调用助理工厂的内部宿主可以显式传入该 loader；未传 loader 时不隐式连接人员数据库。

系统提示词只包含稳定的使用规则；具体员工资料通过 `ContextInjection.supplemental` 作为普通背景数据进入模型，不获得 system/tool 角色。保留原补充材料，不改写树历史、权威工作区、权限或私有审计。只展示服务所需资料，不附带权限、头像、凭据或无关员工信息。

## 实际注入格式

在职状态属于所属员工事实，不能仅凭该字段推断钉钉是否可达；本次不增加自动禁止发送或停用助理的规则。默认值、迁移及维护方式见[员工在职状态](../../data/personnel.md#员工在职状态)。

员工信息直接展示七项：姓名、用户ID、在职状态、所属一级部门、职位、所属主管、所属主管ID。以首尾边界包络，并在身份、部门职位、主管三组之间留白；不展示部门 ID，部门逐行列出，不使用 YAML 或 JSON。

以下是[实际构建器](../../../../app/agent/assistant/context.py)使用虚构资料生成的个人信息段，位于当前任务 user 消息的“上下文资料”中，外层仍由 Core 自适应文本围栏保护：

```text
【员工个人信息】
来源：企业员工资料：当前已保存的姓名、部门和任职记录
确认状态：已确认的记录
════════════ 所属用户信息 ════════════

姓名：张明
用户ID：employee-zhang
在职状态：在职

所属一级部门：
· 研发部
· 产品部
职位：研发工程师

所属主管：李经理
所属主管ID：employee-li

════════════ 用户信息结束 ════════════
```

来源及确认状态只作为简短说明保留，七项资料按三组直接列出，首尾边界与既有工具资料页的展示风格一致。未知字段展示为“未知”，数据库值仍保持原有 null；主管尚未建档时可保留其 userid、姓名显示未知。字段中的换行以字面 `\n`、`\r` 展示，避免伪造其他信息行，不修改数据库原文。

原有补充资料直接保留在前，其他宿主提供的偏好或记忆分别使用 `【服务偏好】`、`【相关记忆】`标题；空分组不展示，个人背景完全为空时原补充资料不变。每份材料仍保留来源和确认状态：confirmed → 已确认的记录，user_reported → 用户陈述，unverified → 待核实，conflicted → 存在冲突。内部 `AssistantContext`和 `ContextMaterial`契约不变，资料不获得 system/tool 角色。

员工信息的简化不改变后文画像列表的分层展示契约；查询、分页及逐条增删均已接入。

## 画像语义与提示词

[个人信息提示词](../../../../app/agent/assistant/prompt/personal_information.py)说明如何结合员工事实资料服务；[画像提示词](../../../../app/agent/assistant/prompt/portrait.py)说明私有画像的对象、一条偏好的含义和查询管理顺序。两者通过[助理提示词组合入口](../../../../app/agent/assistant/prompt/__init__.py)进入全部四类助理任务，探索模式不加载这两部分。

画像目标只用准确员工 `userid` 关联，不再存 `employee/assistant` 类型：

| 相对当前助理的关系 | 目标含义 | 名称展示 |
| --- | --- | --- |
| 目标 userid 等于所属用户 userid | 所属用户本人 | 张明（关系为所属用户） |
| 目标 userid 为其他员工 | 该员工的 AI 助理，作为其代理参与协作 | 李娜的助理 |

同一目标只有一个分组，分组下可有多条画像，每条画像是一项偏好或协作理解。同名对象仍按 userid 区分；姓名只用于检索和展示，不复制到每一条存储记录中作为关联键。

例如张明助理可以保存张明本人的两条偏好，以及李娜助理的三条偏好；不会再为员工李娜本人创建另一套记录。李娜助理拥有自己的私有画像库，不会自动看到张明助理保存的这些条目。

### 逐条存储的逻辑契约

存储以独立行保存，而不是一个对象对应一份整体 JSON：

| 字段 | 用途 |
| --- | --- |
| `owner_userid` | 当前助理所属员工 userid，由可信宿主绑定，不是模型参数 |
| `subject_userid` | 目标 userid，按上表解释本人或其他助理 |
| `key` | 存储端递增分配的稳定正整数偏好标识，不重排、不复用，允许空号 |
| `preference` | 这一条完整偏好文本，可以说明必要的依据、情境和待确认之处 |

不再按 understanding/preferences 两组存储，不要求额外 basis/status 字段。模型仍应区分明确陈述、转述、互动观察及推断，可在偏好文本中说明；一条观察不能被直接扩大为其用户永久不变的性格或企业事实。

姓名、部门和职位等企业事实仍使用员工资料；画像不修改事实或权限。本轮明确要求优先于旧偏好，不自动向其他助理披露私有画像。缺少真实工具或成功回执时，不声称已经保存或删除。

## 工具契约与查询实现

[portrait_contract.py](../../../../app/agent/assistant/tool/portrait_contract.py)维护参数、结果和 `render_portrait_groups`展示；目标、单条偏好和分组数据模型放在[assistant_portrait.py](../../../../app/model/assistant_portrait.py)。[portrait_query.py](../../../../app/agent/assistant/tool/portrait_query.py)实现并注册名称查询和分页工具；[portrait_mutation.py](../../../../app/agent/assistant/tool/portrait_mutation.py)提供新增、删除预验，由助理检查点钩子同事务提交。`PORTRAIT_TOOL_CONTRACTS`本身只是四项契约清单，四个工具均由消费宿主按当前身份装配。

| 工具 | 输入 | 成功结果及语义 |
| --- | --- | --- |
| `search_portraits` | `name` | 按所属用户姓名或其他助理名称查询私有画像；返回 `query_id`、对象数、画像条数、总页数 |
| `view_portrait_query` | `query_id`、`page` | 按结果集分页，返回程序分层渲染的正文及页码、总页数、是否有后续页 |
| `add_portrait` | `subject.userid`、`preference` | 向目标追加一条偏好，返回单条画像及其 ID，不覆盖其他条目 |
| `delete_portrait` | `key` | 仅删除当前助理私有范围内的这一条，其他条目保留 |

### 名称检索与分页

`query_id`就是画像列表的结果集 ID，沿用现有查询工具命名；它和员工 userid、单条偏好的数字 key 是不同的标识。名称按当前所属用户姓名或其他助理所属员工姓名全文检索，末尾“的助理”会移除后再检索，例如“李娜的助理”使用“李娜”。执行器只接收 `name`，画像库所有者由可信宿主绑定，模型不能切换所有者。

结果集只包含有画像的匹配对象，分页单位为目标对象，不把同一目标拆成多页；每组列出该对象在查询快照中的全部画像。对象数量与画像条数分别统计。没有匹配画像时 `query_id=null`、三个计数均为 0；查询失败不能伪装成无画像。没有画像也不等于员工不存在：新建目标可使用已注入的本人 userid，或通过已提供的人员查询工具确认其他助理的准确标识。

结果集已绑定当前助理及本次任务，使用稳定快照分页，不能读取其他助理或其他查询工具的结果。失效时重新搜索；同名无法区分时先澄清，不凭结果顺序选人。

### 全文检索与 LRU 结果集

[AssistantPortraitRepository.search](../../../../app/repository/assistant_portrait.py)在同一事务快照内先查询有当前助理画像的目标，再批量读取这些目标的全部偏好。两条 SQL 均带 `owner_userid`过滤，不先截取全员目录再筛画像。名称使用 `MATCH(employees.name) AGAINST(... IN NATURAL LANGUAGE MODE)`，复用 013 迁移的 ngram 全文索引，`LIKE`字面包含补充单字/短词；`%`、`_`按普通字符处理，查询值全部绑定参数。

排序为完整姓名匹配优先、全文相关性降序，再按姓名和 userid 稳定排序；每个对象内的偏好按数字 key 升序。姓名不复制到画像表，不建立第二套人员权威源。

缓存直接复用已有[QueryResultPool](../../../../app/agent/core/query_pool.py)，不设计或继承新的缓存结构：

- 每轮消费独立创建结果池，用户和任务之间不共享，任务结束立即 `close()`。
- 查询动作权威提交后才发布结果集；未提交或关闭后迟到的提交不能暴露结果。
- 查看动作提交后刷新 LRU 顺序；无效页码、失败或未提交的查看不刷新。
- 容量超限淘汰最久未使用结果集，旧 ID 不能恢复或自动回退全库。
- 查看返回轻量分页元数据和可折叠页面引用，正文通过签名校验后展示；淘汰、关闭或跨任务引用返回页面不可用。

容量、每页对象数和最多匹配对象数复用 `ASSISTANT_DIRECTORY_CACHE_CAPACITY`、`ASSISTANT_DIRECTORY_PAGE_SIZE`和 `ASSISTANT_DIRECTORY_MAX_RESULTS`。查询额外读取一个对象判断截断；`truncated=true`时计数仅覆盖保留的快照，应缩小姓名关键词。数据更新后既有结果集不变，需要新查询获取最新快照。

### 层级展示示例

以下为 `render_portrait_groups`生成的格式示意。姓名使用虚构员工：

```text
════════════ 用户画像查询结果 ════════════
结果集ID：portrait-query-example
第 1 / 1 页
偏好 key 是固定删除标识，不是本页序号。

◆ 张明（所属用户）
用户ID：employee-zhang
在职状态：在职

  偏好 key：1
  偏好内容：
    本人明确要求工作答复先给结论，再给依据。

  偏好 key：2
  偏好内容：
    金额统一保留两位小数。

──────── 用户画像结束 ────────

◆ 李娜的助理
用户ID：employee-li

  偏好 key：3
  偏好内容：
    对方助理明确要求协作请求按背景和待办分段。

──────── 用户画像结束 ────────

已到最后一页。
════════════ 第 1 / 1 页结束 ════════════
```

展示函数接收页码和总页数，以首尾边界、用户分组及偏好条目分层展示；结果集 ID 已包含在真实工具回执中，实际页面正文不重复展示，独立预览时可以显式传入。宿主绑定的 `owner_userid`决定显示为所属用户或其他助理，模型不能指定画像库所有者。姓名中的换行显示为转义字符；偏好多行正文统一缩进保留，不解释为新用户分组或系统指令。重复目标分组、同组或跨组重复 key、空页及无效页码明确拒绝。

每条偏好明确标出 `偏好 key`，同一用户内按 key 从小到大展示。key 是存储端递增分配的稳定标识，不是页面序号，也不按用户分组从 1 重新生成。删除条目后保留其余 key，例如 2、5、9；翻页、再次查询或删除其他条目后都不能重排。新增结果和删除参数使用相同的严格正整数 `key`，拒绝布尔值、字符串数字、0 及负数。

### 单条新增与删除

新增输入示例：

```json
{
  "subject": {"userid": "employee-li"},
  "preference": "对方助理明确要求协作请求按背景和待办分段。"
}
```

删除输入示例：

```json
{"key": 3}
```

新增不接收整份画像、类型字段或版本号，一次只写一条并返回固定数字 key；删除不接收 userid 或整对象参数。若需修正，先确认具体条目，再分别执行新增和删除；两步各自有独立结果，不能当作已提供原子修改工具。

新增执行器先校验目标员工存在和偏好 UTF-8 大小不超过 65535 字节，再预留一个稳定数字 key；模型不能指定画像库所有者或自行分配 key。删除预验只在 `owner_userid + key` 范围查找，不能按目标 userid 清空；`deleted=false`只表示当前助理可访问范围内确认已不存在，不泄露其他画像库。结果不确定时不能盲目重试新增或宣称成功。

已实现私有范围查询、稳定分页、结果集生命周期和增删同事务提交；既有 LRU 查询仍是不可变快照，新增或删除后应重新搜索，不就地重排或改写已建立的结果集。

### 同事务提交与恢复

[017 画像动作迁移](https://github.com/caicai-6666/knowledge-accumulation-be/blob/350b1e2/schema/017-assistant-portrait-actions.sql)增加私有序号表和已提交动作去重账本。序号表初始化同时保留画像表的存量最大值及真实自增高水位，避免最高条目删除后回退。迁移读取高水位时临时关闭本连接的统计缓存，随后恢复，不修改全局配置。

工具预验只独立推进数字序号，不提前写画像正文；失败或取消允许留空号。`AssistantPortraitRepository.commit_actions`复用既有提醒工具的方式，在 `MySQLAssistantRepository.commit_hook`中消费节点的已接受工具对：

1. 节点归属与助理任务由既有检查点钩子校验；模型不能传入 owner、任务或动作追踪标识。
2. 用任务和原生工具调用的哈希定位私有去重记录，校验请求与业务回执指纹一致。
3. 新动作在当前 SQL 事务内新增或删除一条画像，同时登记去重记录；与节点正文、工作区版本及任务状态一起提交或回滚。
4. 后续检查点重放相同动作直接跳过；不同参数或回执复用同一调用标识明确拒绝。删除画像后仍保留去重记录，避免重放旧新增让条目复活。

失败调用及纠错反馈仅在 Core 连续纠错期间可见，成功后清除；它们不进入节点已接受轨迹，不产生画像写入。序号、动作哈希和去重账本属于模型上下文之外的工程状态；只有画像目标、偏好及数字 key 属于业务结果。

存储/预验故障返回脱敏失败，不伪装为不存在或完成；检查点提交异常沿用 Core 的停止语义，不作为普通参数纠错反复执行。任务恢复不重新生成已有节点，已提交动作不会重复追加。动作账本不得在任务仍可能重放时提前清理，数字计数器不得重置或复用。

## 多部门背景

所属部门按当前可信员工身份的 `departments` 列表展示全部一级部门名称，以“所属一级部门”为标题逐行列出，无主次含义；排列第一项不代表主部门，不据此推断职位、主管或权限。与助理目录复用 `app/agent/assistant/rendering.py` 的文本展示函数；空资料显示“未知”，不同 ID 的同名部门分别保留。旧模拟身份没有列表时兼容 `department_name`；真实SQL查询已经将历史单部门归一为列表。部门身份不提升文件权限或管理员权限。
