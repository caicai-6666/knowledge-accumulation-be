# 助理记忆驻留与工作区

## 目的与范围

个人助理使用无分支的线性树。进程为每棵已使用的助理树保留一个有效记忆窗口：**最新已提交的上下文压缩摘要＋未被覆盖的后续任务节点＋一个最新工作区**。初始没有摘要时保留已有任务；空树只有空工作区。用户消费工作循环初始化时就恢复启用助理的窗口，空闲等待队列时继续驻留；停用助理释放其窗口。任务结束关闭本轮 Agent 和工具查询池，不清空该助理的记忆窗口。

这里的摘要来自模型上下文压缩，没有额外的摘要生成机制。任务前压缩保存的摘要节点，以及任务内 `context_summary` 检查点，都投影到同一个最新摘要和覆盖边界。历史对话和私有审计继续保存在数据库；按需检索旧历史是临时读取，不加入常驻窗口。

本规则仅适用于 assistant；exploration 继续使用[共享树结构缓存](../../data/question-tree.md#内存构树与正文加载)和历史工作区快照。

## 压缩提交与驱逐

[节点检查点](../../../../app/repository/node_persistence.py)提交压缩结果时，[assistant_memory.py](../../../../app/repository/assistant_memory.py)只处理本次新增的 `context_summary`，按 `covered_turns` 消费当前继承历史的前缀。被覆盖的节点及其公开消息从驻留窗口移除，最新摘要替换旧摘要，当前执行任务永不参与前缀驱逐。

例如驻留任务为 `A、B、C`，正在执行 `D`，压缩覆盖 2 个历史任务后，窗口为 `新摘要＋C、D＋最新工作区`；同轮再次覆盖 C 后变为 `更新的摘要＋D＋最新工作区`。完整检查点重放不重复驱逐；越界数量、非法摘要、SQL 错误或取消使整次提交回滚，不发布新的摘要、工作区或内存窗口。

任务前压缩覆盖全部有效历史时，摘要与新任务在同一事务登记，并同时保存整理后的最新工作区。已存摘要节点仍可用于历史审计，常驻窗口直接保存其有效文本，不继续持有被它覆盖的节点。节点内的原始压缩检查点保留在 SQL，驻留正文剔除这些已投影标记，避免下一轮重复应用覆盖数量或累积旧摘要。

[AssistantMemoryCache](../../../../app/service/assistant_memory.py)由共享树仓库持有，键为 `(owner_userid, tree_id)`，跨任务复用。SQL 提交确认后才替换窗口；事务内临时状态不对其他任务可见。旧版本迟到提交不能覆盖较新驻留，回滚/提交不确定时撤销本地驻留，下一次从权威数据恢复。停机释放全部窗口；没有按节点数或闲置时长额外淘汰窗口的机制，规模取决于已使用助理数和各自有效上下文大小。

## 冷启动与数据库存储

[021 迁移](../../../../schema/021-assistant-current-workspace.sql)新增 `assistant_workspaces`，每棵树只有一行：

| 字段 | 含义 |
| --- | --- |
| `tree_id` | 主键，一棵助理树仅有一个当前状态 |
| `id`、`content`、`created_at` | 当前工作区的版本标识、正文及版本创建时间；更新时覆盖同一行，不保留旧正文 |
| `summary` | 最新已提交压缩摘要；未发生压缩时为 null |
| `first_sequence` | 未被覆盖的首个任务序号；冷启动 SQL 的读取下界 |
| `updated_at` | 当前状态最近更新时间 |

先读取权威树行校验归属和 revision。同版本直接复用驻留窗口；未命中时先读取上述单行状态，再通过 `sequence >= first_sequence` 查询有效任务，批量读取其正文和公开消息。已覆盖节点不会先加载再截断，也不会逐节点加载工作区快照。摘要之前的父节点引用允许留在磁盘，窗口只校验自身保留节点的连续性及主干末端。

助理节点的 `workspace_version_id` 统一为 null，不再绑定历史工作区。`load_node` 读取助理历史任务时返回当前工作区，不能用它恢复过去某个节点时的工作区；历史原始生成和工具轨迹仍可审计。探索模式仍以每个节点绑定的不可变工作区版本恢复。

初始化上下文由 `summary`、有效任务正文和唯一工作区构建，已完成中途消息单独投影。节点私有生成不进入驻留窗口；本轮生成需要的局部副本、按需历史检索和数据库驱动缓冲不属于长期驻留缓存。

## 显式迁移与部署

应用不自动执行 DDL 或清理历史数据。部署须先停止所有可能写入个人助理的旧进程，确认没有生成中的助理节点：

1. 手工执行 `schema/021-assistant-current-workspace.sql` 创建状态表。
2. 在本项目环境运行 `python -m app.repository.assistant_memory_migration`。
3. 确认每棵助理树恰好一条当前工作区，旧 `question_workspaces` 中没有 assistant 快照，助理节点没有历史工作区引用，再启动新代码。

迁移器按树持行锁，在同一事务中读取最近摘要边界的旧历史、顺序投影已接受压缩检查点、复制主干末端的最新工作区、解除节点引用并删除该树旧工作区快照；最后验证新窗口。任何缺失、损坏或生成中状态使该树迁移失败并保留旧数据。已经完成的树可跳过重跑；多棵树不是一个整体事务。工具只输出计数，不输出用户正文或凭据。

升级后无法恢复已删除的历史工作区正文。旧版服务不能重新启动写入；如果需要回退，应使用部署前独立备份，而不是仅回退代码。新建助理从第一次建树起就创建单行状态，启动检查验证新表存在。

依赖节点检查点、树事务、现有 Core 压缩协议和工作区模型。未修改模型工具参数或压缩提示词，不改变 exploration 的注入范围。历史检索仍沿已授权祖先范围按需读取，工具结果 LRU 与常驻窗口互相独立。
