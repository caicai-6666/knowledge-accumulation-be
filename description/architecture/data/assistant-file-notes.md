# 上传文件元信息与个人助理备忘

> **当前部署入口：** 新空库仅执行 deploy 的[最新初始化脚本](../../../../knowledge-accumulation-deploy/mysql/init/001-schema.sql)。本文中的编号迁移和旧库操作属于历史演进记录，不是新部署步骤；历史 SQL 已从当前仓库移除，仅可从 Git 历史追溯。已有数据库须另行制定升级方案，不可重跑初始化。

## 用途与实现状态

上传元信息仅为个人助理接收的附件记录上传者、上传时间、类型及可见范围；个人备忘记录某位用户为该文件拟定的名称和摘要，帮助后续检索取回文件 UUID。同一文件可由多个用户分别记录，每位用户最多记录一次。

**已提供 MySQL 表结构、手工迁移、个人助理新附件自动登记，以及个人助理查看/修改文件可见范围、备忘新增/删除、结构化查找与结果集查看工具。** 尚未接入批量历史文件回填、备忘修改工具和跨用户读取授权。`public` 不会自动开放跨用户访问；个人助理附件查看工具在[附件归属校验](question-file.md)之外要求文件公开，所属用户本人的私密文件也拒绝查看。探索、HTTP 与注册中心读取不新增此限制。

## 表结构

[023 迁移](https://github.com/caicai-6666/knowledge-accumulation-be/blob/350b1e2/schema/023-assistant-file-notes.sql)保留初版表结构历史，[024 迁移](https://github.com/caicai-6666/knowledge-accumulation-be/blob/350b1e2/schema/024-uploaded-files-and-personal-notes.sql)将其调整为以下两张表。

### 文件元信息 uploaded_files

| 字段 | 类型与约束 | 含义 |
| --- | --- | --- |
| `id` | `CHAR(36)`，主键 | 现有附件的小写带连字符 UUID，不额外生成文件 ID。 |
| `owner_userid` | `VARCHAR(128)`，非空白，区分大小写 | 文件上传者，由可信上传身份确定。 |
| `type` | `VARCHAR(16)`，必填 | 精确取值 `images`、`audio`、`video`，与现有附件引用一致；PDF 属于 `images`。 |
| `visibility` | `VARCHAR(16)`，默认 `public` | 文件可见范围标记，精确取值 `public` 或 `private`；程序只允许上传者修改。 |
| `uploaded_at` | `DATETIME(6)`，必填 | 可信上传流程的 UTC 接收时间，具体来源见下方登记流程；不是源文件创建时间。 |
| `updated_at` | `DATETIME(6)`，必填 | 文件元信息最近更新时间，UTC，由程序维护，不早于上传时间。 |

索引 `(owner_userid, uploaded_at, id)` 支持按上传者查看文件。文件字节仍由原有附件存储负责，本表不复制文件内容。

### 个人备忘 assistant_file_notes

| 字段 | 类型与约束 | 含义 |
| --- | --- | --- |
| `owner_userid` | `VARCHAR(128)`，非空白，联合主键 | 记录者所属用户，由当前助理的可信用户身份绑定，可以不同于文件上传者。 |
| `file_id` | `CHAR(36)`，联合主键、外键 | 引用 `uploaded_files.id`。 |
| `name` | `VARCHAR(200)`，非空白 | 模型拟定或与用户协商的名称，不要求等于原始文件名。 |
| `summary` | `TEXT`，非空白 | 文件内容和用途摘要，容量受 MySQL TEXT 字节上限约束。 |
| `updated_at` | `DATETIME(6)`，必填 | 个人备忘最近更新时间，UTC，由程序维护。 |

联合主键 `(owner_userid, file_id)` 保证每位用户对同一文件最多一条备忘；不另设备忘 ID。文件的上传时间、可见范围通过关联文件表取得，不在各用户备忘中重复保存。索引 `(owner_userid, updated_at, file_id)` 支持查看个人最近更新记录，`(file_id)` 支持外键及按文件查找关联备忘。另由 [025 迁移](https://github.com/caicai-6666/knowledge-accumulation-be/blob/350b1e2/schema/025-assistant-file-notes-fulltext.sql)增加联合全文索引 `ft_assistant_file_notes_name_summary (name, summary) WITH PARSER ngram`；暂不引入向量索引。

两表均使用 InnoDB、`utf8mb4`；名称与摘要采用 `utf8mb4_0900_ai_ci`，用户标识采用 `utf8mb4_0900_bin`，UUID、类型与可见范围采用 `ascii_bin`。

## 转换完成后的自动登记

[UploadedFileRegistrationService](../../../app/service/uploaded_file.py)负责元信息登记与清理协调，[UploadedFileRepository](../../../app/repository/uploaded_file.py)复用项目已有 MySQL 事务，[UploadedFileRecord](../../../app/model/uploaded_file.py)校验 UUID、类型、归属及带时区时间。组合根 [main.py](../../../app/main.py)装配登记服务，仅由个人助理附件转存流程新增记录；整树清理保留对早期探索元信息的兼容删除。文件存储层仍只负责 I/O，不引入数据库依赖。

| 入口 | 登记时机与来源 |
| --- | --- |
| 探索上传 | 不写入 `uploaded_files`；仍保存文件并由任务附件引用负责归属与读取授权。 |
| 钉钉及中间件助理附件 | 钉钉图片先转换成 PDF 并可靠暂存，入队后由 `AssistantConsumer._prepare_files` 校验、保存最终文件、登记元信息，再写入任务文件映射并标记 prepared。owner 来自可信队列任务 userid。 |
| 助理合并消息 | 每个文件使用所属原始消息的 `created_at`，不使用合并任务的最晚时间或重试时间；无原始消息分组的任务使用其可信任务 `created_at`。时间表示队列接收，不宣称是钉钉客户端的原始上传时间。 |

机器人收件箱中的临时 UUID 与最终任务 UUID 不同，临时副本确认发布后会被清理，因此不登记临时副本。`uploaded_files.id` 必须等于最终 `TaskContent.attachments.file_id`。转换失败、内容校验失败或磁盘保存失败的附件不登记；元信息默认公开，但不会创建个人备忘或开放现有读取权限。

服务的 `register(reference, owner_userid, uploaded_at=...)` 是可信宿主接口，调用前必须完成格式转换/校验和持久落盘，不能直接暴露给客户端或模型。重复 UUID 通过数据库唯一键幂等处理：已有归属、类型必须相同；保持已有可见范围、上传时间及更新时间，不因重试将私密文件改回公开。归属或类型冲突明确失败，不覆盖记录。

### 失败、取消与清理

- 探索批次在任务登记前失败或取消时，仅补偿本批新文件，不查询或写入上传元信息表。任务已经登记的附件不补偿删除。
- 助理登记失败不进入 prepared、不启动生成、不确认消费。稳定 UUID 与持久映射支持下一次消费恢复；已保存的文件保留，已存在映射的文件会重新核实磁盘并幂等补齐元信息，不重复下载。
- 整树删除沿用持久化附件清理清单，逐项删除元信息和磁盘文件，成功后才完成清单。元信息或磁盘已删除时重试可继续；历史附件没有元信息也可清理。
- 有个人备忘引用时，外键阻止删除元信息，服务同时保留原文件，不自动删除他人的备忘。整树 SQL 删除可能已完成，附件清理清单会保留，须先处理关联备忘再重试清理。

文件系统与 MySQL 没有共同事务；进程被强制终止、补偿数据库不可用等情况可能留下尚无任务引用的文件或元信息，本次没有新增后台扫描/孤立记录回收。现有读取仍要求任务归属与引用，元信息本身不是访问凭据。个人助理接收新附件必须装配登记服务，缺少服务时显式失败；探索文件服务不依赖该服务。范围收窄不删除已有元信息，不增加来源字段或执行历史数据迁移；旧探索记录仍保留，仅在原有整树删除流程中协调清理。

## 文件可见范围工具

个人助理由消费宿主逐任务注入 [FileVisibilityTools](../../../app/agent/assistant/tool/file_visibility.py)，绑定当前认证用户；探索模式不注册这两个工具。工具不要求先搜索备忘，直接使用完整文件 UUID。

| 工具 | 必填参数 | 模型看到的成功正文 |
| --- | --- | --- |
| `get_file_visibility` | `file_id` | 查询状态、文件 ID、中文可见范围与枚举值、文件上传时间、元信息更新时间。 |
| `set_file_visibility` | `file_id`、`visibility` | 修改状态与上述文件字段；已是目标值时明确“无需修改”，时间保持不变。 |

参数来自 Pydantic Schema，UUID 必须是完整小写带连字符形式，`visibility` 仅接受 `public`、`private`，不接受 null、未知字段或自定义 owner。文件上传时间取自 `uploaded_files.uploaded_at`，与元信息更新时间均使用带 UTC 偏移的 ISO 8601 字符串；修改可见范围不会重置上传时间。

例如确认文件范围时调用 `get_file_visibility(file_id="已知文件UUID")`；所属用户明确要求设为私密时调用 `set_file_visibility(file_id="已知文件UUID", visibility="private")`。修改不要求预先查看，但必须依据所属用户意图，不能把其他助理的请求视为授权。

### 模型可见反馈格式

两个工具的 `role=tool` 正文均由各自注册的末尾渲染钩子生成带标题的文本，不是纯 JSON，也不是 JSON 中的 text 字段。成功展示执行状态和业务字段，失败展示状态、具体原因及下一步。下例 ID 与时间为示例：

```text
### 文件可见范围修改

状态：修改成功
文件 ID：12345678-1234-1234-1234-123456789abc
可见范围：私密（private）
文件上传时间：2026-11-08T02:00:00+00:00
元信息更新时间：2026-11-09T08:00:00+00:00
```

```text
### 文件可见范围修改

状态：修改失败
原因：该文件不属于当前所属用户，无权修改可见范围，本次未修改。
下一步：请由文件上传者的助理操作；如选错文件，请改用所属用户上传的文件 ID。
```

程序内仍保留 `tool_result` 的 `file_id`、`visibility`、`uploaded_at`、`updated_at`、`changed` 或 `code/message`，错误码用于拒绝审计，不在模型正文中展示。已接受历史保存排版后的工具正文，后续上下文沿用同一展示；不从这段文本反解析权限或执行更新。未知结果仍由 Core 直接终止，不宣称模型收到了该反馈。

### 权限与执行语义

`FileVisibilityService` 复用 [uploaded_file.py](../../../app/service/uploaded_file.py) 的输入校验，[UploadedFileRepository](../../../app/repository/uploaded_file.py)先按文件 ID 查询登记记录，再在同一事务内核对上传归属；更新 SQL 仍同时限定 `id + owner_userid`。仅上传者的助理可查看或修改；其他用户只会得到权限拒绝，不返回上传者身份、可见范围或其他元信息。拥有一条个人备忘不会授予原文件管理权限。

修改在独立数据库事务中锁定文件行、再次核对归属并更新，提交确认后才返回成功。新值与旧值不同才更新 `updated_at`，保持时间递增；不改变 `uploaded_at`、上传者、类型、任务正文或备忘。直接设为目标值满足幂等语义，不使用“切换”动作。

文件元信息是可见范围的权威状态；已接受的工具回执只记录当时确认值，后续要了解最新状态应重新查询。修改不依赖问答树结构或最终 `finish_task` 提交。若元信息提交成功后问答检查点失败，已确认的修改仍保留，Core 停止且不自动重放；恢复后先查询实际状态，不假设修改随问答失败回滚。

**可见范围工具只管理元信息；个人助理附件查看已单独消费该标记。** 该查看工具要求 `public`，并在缓存读取及页面再次展示时重查。跨用户文件读取仍未接入，`public` 不代表已分享或其他助理已能读取。通用读取服务继续校验原有任务归属，不增加此限制；详见[图像阅读](../workflow/question-answering/image-reading.md)。

### 失败反馈与上下文

以下错误码用于程序分支和审计，模型正文呈现对应的原因与修正动作。

- 元信息表没有该 ID 时返回 `file_not_registered`：仅说明未找到上传登记记录，指引核对完整 ID，确认无误后先完成登记再操作；不能据此推断原文件不存在或上传尚未结束。
- 已有登记但上传者不是当前所属用户时返回 `file_permission_denied`：明确无权查看/修改，指引由上传者的助理操作，或在选错文件时换用本人上传的 ID。不返回上传者身份、文件可见范围等资料。此反馈区分了未登记与无权限，但不开放元信息查看。
- 两类错误的具体原因及修正方向在仓库校验分支就近维护，工具原样保留错误码和定向反馈；查看失败说明未返回可见范围/文件信息，修改失败说明本次未修改，不混入备忘相关指引。
- 参数格式错误由 Core 根据实际 Schema 反馈；只有明确合法值才能进入仓库。查询或更新前的依赖故障返回 `file_visibility_unavailable`，不能伪装为空结果或已修改。
- 已尝试数据库更新但无法确认提交时返回 `unknown / file_visibility_update_unknown`。Core 停止，不重复执行；此终止分支没有下一轮模型请求，不能声称恢复指引已送达模型。
- 可纠正失败的工具调用与定向反馈只留在连续纠错上下文中；成功后由 Core 清除整段失败轨迹，原始生成与拒绝事件保留在私有审计。失败轨迹不写入权威工作区和已接受历史。

## 备忘新增与删除工具

[FileNoteTools](../../../app/agent/assistant/tool/file_note.py) 由消费宿主绑定当前所属用户并注入，探索模式不提供。模型与仓库分别维护字段校验，记录模型见 [assistant_file_note.py](../../../app/model/assistant_file_note.py)，数据库操作见 [AssistantFileNoteRepository](../../../app/repository/assistant_file_note.py)。无需新增表或迁移，依赖既有 024 表结构。

| 工具 | 参数 | 行为 |
| --- | --- | --- |
| `add_file_note` | `file_id`、`name`、`summary` | 只为所属用户上传且已登记的文件新增；同用户同文件已存在时拒绝覆盖。 |
| `delete_file_note` | `file_id` | 仅删除当前记录者对应条目；没有记录时返回无需删除。 |

名称去除首尾空白后为 1 至 200 字符，摘要去除首尾空白后非空且 UTF-8 最多 65535 字节。文件 ID 使用现有 UUID，不新增备忘 ID。记录者与更新时间由程序确定；新增反馈同时展示文件上传时间。私密文件允许根据用户提供的信息记账，不代表助理可以读取原文；两个工具不改变可见范围、原文件、上传元信息或其他用户的备忘。当前不开放为他人上传文件新增备忘，表结构仍保留多记录者能力。

新增先锁定上传文件行，检查登记、上传归属及本人重复记录，再插入条目；唯一键保证最终唯一性。删除锁定本人条目后执行删除，已不存在为无变化。采用独立数据库事务，确认提交后才返回成功；随后问答检查点失败不会回滚已确认的备忘变更。已尝试写入但提交结果无法确认时返回 `unknown`，Core 终止且不自动重放，不声称模型收到下一轮反馈。未知写入结果仍要求管理员核对实际记录，不自动重放。

每个工具独立注册末尾渲染钩子，结构化结果留给程序；错误原因和修正方向在产生校验的仓库或工具分支维护。可纠正失败只保留在连续纠错阶段，成功后清除，私有审计保留。示例：

```text
### 文件备忘新增

状态：已创建
文件 ID：12345678-1234-1234-1234-123456789abc
名称：采购合同
摘要：
> 用户提供的采购合同说明。
文件上传时间：2026-11-09T01:00:00+00:00
备忘更新时间：2026-11-09T02:00:00+00:00
```

```text
### 文件备忘删除

状态：备忘已不存在，无需删除
文件 ID：12345678-1234-1234-1234-123456789abc
```

缺少上传登记、非本人上传或重复备忘均返回具体原因与修正方向，不覆盖已有条目，不诱导自动删除重建；依赖检查失败不伪装成不存在。名称中的换行转义、摘要以引用段展示，避免资料伪装成执行状态字段。

## 备忘查找与结果集查看

[FileNoteQueryTools](../../../app/agent/assistant/tool/file_note_query.py)由助理消费宿主按本轮用户绑定，每任务独立实例；不调用子智能体，不提供给探索模式。仓库 [search](../../../app/repository/assistant_file_note.py) 使用参数化 SQL，始终限定备忘记录者 `owner_userid`，关联上传表取得上传时间，不要求文件公开，也不读取原文件。

| 工具 | 参数 | 行为 |
| --- | --- | --- |
| `search_file_notes` | `query_id` 可选 | 不传搜索本人全部备忘；传入则仅在该旧结果集保留的文件 ID 范围内回查当前记录。 |
| 同上 | `name_keyword`、`summary_keyword` 可选 | 分别匹配名称与摘要；null、空白或省略跳过对应条件。两者均不传时浏览或只按时间筛选。 |
| 同上 | `match_mode=and/or`，默认 and | 仅组合两路文本条件；只提供一路时不影响结果。 |
| 同上 | `time_field=uploaded_at/updated_at`，默认 updated_at；`start_time`、`end_time` 可选 | 上传时间或备忘更新时间；带时区，开始包含、结束不包含。时间始终与文本及旧结果范围额外 AND。 |
| `view_file_note_query` | `query_id`、`page` 必填 | 页码从 1 开始，每页 10 条，展示文件 ID、名称、摘要、上传时间和备忘更新时间。 |

例如 `search_file_notes(name_keyword="合同", summary_keyword="付款", match_mode="and")` 要求名称匹配合同且摘要匹配付款；or 只要求任一路匹配。继续筛选时传入旧 query_id 与新条件，成功返回新结果集 ID，旧结果不改写。已删除条目不进入新结果，已有条目的名称和摘要回查当前 SQL；旧页面仍是查询时快照。查询按备忘更新时间倒序、文件 ID 升序稳定排序，不按相关分数排名。

### LRU 与结果范围

`FileNoteQueryPool` 复用 Core 查询池，每任务最多 10 个结果集、每集最多保留 1000 条。新查询或继续筛选的结果只有在 Core 成功提交后发布；成功查看刷新该结果的活跃顺序，成功继续筛选（包括零匹配）刷新父结果，再发布新结果。失败、未提交调用和页面自动重新展示不刷新 LRU。超过容量淘汰最久未使用的结果，任务结束统一释放；其他任务或其他用户的 ID 不可使用，失效时返回定向提示，绝不自动取消范围限制。

仓库多取一条判断截断。继续筛选继承父结果的截断限制，纵使新结果很少也不能当作原始全范围的完整匹配；回执与查看页回执始终保留该提示。空结果返回数量 0 和无查询 ID，不创建空缓存。筛选期间父结果被释放时拒绝发布，不返回不完整的伪成功。

两个工具各自注册末尾渲染钩子，模型收到中文业务回执，内部结果保持结构化。查看提供资料可见、隐藏、不可读三态回执，资料由签名页面引用读取，不把整页正文塞进历史。查询失败不等于无备忘，页码越界与 ID 失效分别保留具体修正方向；成功后清除失败轨迹，私有审计保留。

### 独立字段全文索引与部署

[026 迁移](https://github.com/caicai-6666/knowledge-accumulation-be/blob/350b1e2/schema/026-assistant-file-notes-field-fulltext.sql)增加 `FULLTEXT(name)` 与 `FULLTEXT(summary)` 两个独立 `ngram` 索引，SQL 分别使用 `MATCH(n.name)`、`MATCH(n.summary)` 后组合 AND/OR。原 025 联合索引保留兼容，但不能代替两个独立索引。关键词使用自然语言模式，不解析用户提供的布尔查询语法；不回退 LIKE。`ngram_token_size=2` 时单字和停用词可能无匹配，全文检索不等于字面包含或语义理解。

在既有表结构准备完成后手工执行 026；应用启动不自动迁移。InnoDB 每条 ALTER 只能创建一个 FULLTEXT 索引，文件分两条执行，DDL 不具备共同回滚：若中途失败，应先回查索引，只补缺少的步骤。缺少索引时查询明确失败，不伪装为空结果。无需新增环境变量。

## 归属、权限与删除边界

例如 A 上传文件，A 与 B 在拥有读取权限时可以分别建立自己的备忘：文件的 `owner_userid` 始终为 A，备忘的 `owner_userid` 分别为 A 和 B。备忘归记录者所有，文件公开不意味着个人备忘公开。

当前可见范围工具已校验上传归属；备忘与共享读取后续接入仍须落实以下规则，数据库外键本身不代表授权：

- 上传者和记录者身份由程序确定，模型不能指定其他用户冒记；每位助理仅查询、修改、删除自己所属用户的备忘。
- 新建备忘时检查文件登记与当前读取权限，仅知道 UUID 不足以取得权限。
- 只有上传者能修改文件可见范围。文件由公开改为私密后，其他人的备忘可以保留，但读原文件时必须重新校验权限，包括阅读缓存命中时。
- 删除个人备忘不会删除文件元信息、原文件或其他人的备忘。
- 文件外键采用 `ON DELETE RESTRICT / ON UPDATE RESTRICT`，仍被备忘引用时拒绝删除元信息或修改文件 UUID。现有清理服务先删除元信息，再删除磁盘文件；不进行隐式级联删除，关联备忘仍须显式处理。

用户字段暂不增加员工表外键，以免将人员同步生命周期与文件、备忘历史绑定。备忘更新时间与文件上传时间分属两表，跨表时序如需校验由后续服务负责。

1. 使用本项目 `MYSQL_*` 指向的数据库，先执行 `schema/023-assistant-file-notes.sql`；已执行过的环境不重复执行。
2. 执行 024 前确认 `assistant_file_notes` 为空、暂无写入方，且 `uploaded_files` 不存在。本次设计调整对应尚未接入业务的空表。
3. 手工执行 `schema/024-uploaded-files-and-personal-notes.sql`，创建文件元信息表并调整备忘结构。
4. 手工执行 `schema/025-assistant-file-notes-fulltext.sql`，为名称和摘要增加中文联合全文索引。025 可用于已有备忘数据的表，会为已有文本建立索引；大表应安排维护窗口，建索引可能重建表。
5. 回查字段、主键、外键、CHECK、索引及行数，确认符合本契约。

若旧备忘表已有记录，须停止并单独核实文件真实上传者、类型和记录者后制定迁移方案，不能直接将旧 owner 当成上传者或伪造上传时间。迁移由两条 DDL 组成，不具备跨语句事务回滚；若建表成功而 ALTER 失败，新文件表会保留，应先检查结构与数据再处理，不能盲目重跑。隔离测试确认：未准备文件父记录时，非空旧备忘表的 ALTER 因外键校验失败，旧备忘数据与原结构保留。

新上传接入前须先准备 023、024；025 用于备忘全文检索。缺表时上传登记失败，不降级跳过登记，应用不自动建表。此变更无需新增迁移或环境变量，不执行历史批量回填，不自动创建备忘，不修改任务 JSON 契约及读取授权。助理待消费任务重试时可用其可信原始消息时间补齐已有文件映射的元信息；其他历史附件保持原状。
